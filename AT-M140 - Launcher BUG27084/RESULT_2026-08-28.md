Weather 설치 패키지는 `com.weatherteam.rainy.forecast.radar.widgets`이고 `com.innovative.weather.app.widget.*`는 provider 클래스 네임스페이스다. 동일 앱의 7.7.8과 7.8.2, 그리고 패키지·서명이 다른 AccuWeather에서 재현됐으므로 **특정 Weather 앱·특정 버전 한정 결함은 아니다.** 직접 관찰 범위에서는 다른 3rd-party 날씨앱까지 위험이 확장됐다.

개발사가 지목한 경로는 Weather 전용 코드가 아니라 provider를 찾지 못한 generic `PendingAppWidgetHostView`에서 `updateAppWidget(null)`을 처리하는 Launcher 코드다. 따라서 비날씨 3rd-party 위젯에도 동일 stale provider 상태가 생기면 구조적 위험이 있다는 가설은 타당하다. 다만 Simple Clock은 유효 AppWidget instance 생성에 실패했으므로 이 범위는 아직 `SUSPECT`이며 직접 재현으로 일반화하지 않는다.

재현 stack은 VoC와 동일하다.

```text
java.lang.NullPointerException: ... equals(...) on a null object reference
  at LauncherAppWidgetHostView.updateAppWidget(LauncherAppWidgetHostView.java:185)
  at PendingAppWidgetHostView.<init>(PendingAppWidgetHostView.java:88)
  at Launcher.inflateAppWidget(Launcher.java:3559)
```

일반 HOME 복귀 후 화면은 상태바만 남은 검은 화면이었고 `uiautomator dump`는 `null root node`를 반환했다. AppWidgetService에는 Google Go id 2/3만 남았으며 Weather id 9는 없었다. 반면 PendingAppWidgetHostView stack이 발생했으므로 일반 Launcher DB의 stale widget 레코드가 로드됐음을 알 수 있다. LauncherProvider는 signature permission으로 보호되어 shell 직접 query는 거부됐다.

따라서 **Weather 7.7.8 자체 또는 `pm clear`/force-stop만으로는 재현되지 않는다.** 관찰된 상태 생성 경로는 `일반모드에서 WeatherWidget4x1 배치 → 간편모드 전환 → Weather 제거·동일 APK 재설치 → 일반모드 복귀`다. 날씨앱 package lifecycle이 stale 상태를 만드는 trigger이고, crash root cause는 pending widget의 null contentDescription을 처리하지 못한 Launcher 코드다.

이 시점의 crash buffer 최초/최종 시각은 `19:34:29.567` / `19:36:30.388`이며 29건 모두 line 185/88 stack이었다. 이후 대기 중이던 배포 OTA를 데이터 유지 방식으로 적용한 결과는 문서 상단의 추가 검증 절에 기록했다.

## 실행 기록

1. 일반 HOME이 `com.hnlens.launcher3`임을 확인했다.
2. 현재 Play Store 설치본 `7.8.2`의 base + split APK 4개를 pull하고 SHA-256을 저장했다.
3. 재현 전 AppWidgetService에서 `WeatherWidgetHourly`, id 5가 Launcher host에 정상 binding된 것을 확인했다.
4. 승인된 `pm clear`와 `am force-stop`을 적용했다.
5. 재부팅 직전 package 상태는 `stopped=true`였고 id 5 binding은 유지됐다.
6. 재부팅 후 `18:51:30.927` AppWidget broadcast가 Weather process를 시작했다.
7. 재부팅 후 Weather package는 `stopped=false`; Launcher PID 2013과 HOME window는 유지됐다.
8. crash buffer와 process exit-info에서 Launcher NPE는 0건이었다.
9. 스크린샷에서 통신 설정 팝업 뒤 일반 홈 렌더링을 확인했다.

## 원본 로그와의 상관

원본 APLog는 Launcher가 약 35.5초 동안 동일 stack으로 9회 crash한 것을 보여준다.

```text
LoaderTask: Widget provider not found for id=8,
component=.../WeatherWidget4x1
  -> PendingAppWidgetHostView.<init>(line 88)
  -> LauncherAppWidgetHostView.updateAppWidget(line 185)

```

원본 bugreport의 package dump에는 Weather `7.7.8`이 `stopped=true`로 남아 있지만, AppWidgetService의 Widgets 목록에는 Weather id 8이 없다. 반면 Launcher 로그는 DB에서 id 8을 반복 로드한다. 따라서 `Launcher DB stale record ↔ AppWidgetService binding 부재` 불일치가 직접 관찰된다.

## 개발사 답변 평가 갱신

- `LauncherAppWidgetHostView.updateAppWidget(null)`의 null 처리 누락이라는 코드 root-cause는 원본 stack과 정합한다.
- 날씨앱은 root cause가 아니라 trigger를 만든 외부 상태다.
- 개발사가 제시한 `앱 데이터 삭제 + 강제 종료 + 재부팅`만으로는 현재 7.8.2에서 원본 stale-binding 상태가 만들어지지 않았다.
- 개발사 fixed-build 미재현 결과도 original 7.7.8 + `WeatherWidget4x1` + id 8 stale 상태를 먼저 증명하지 않았다면 `runtime PASS` 근거로 부족하다.
