# BUG 27084 — 비날씨 위젯 범위 및 개발사 절차 역검증

## 판정

- 실행일: 2026-08-29 KST
- 단말: AT-M140 (`B06201249E00030C`)
- 적용 빌드: `RY07260901S` (업데이트 UI 표기 `AT-M140SZ0828U`)
- Launcher: `com.hnlens.launcher3` 9.0.1.1314/code1314
- 진단 상태: `OBSERVED`
- 관찰 판정: `BUG-GAP observed`
- 최종 단말 상태: 간편모드 `com.hnlens.simplemode`
- ODIN2 (`f2bfcc3c`): 연결 상태만 확인, 변경 없음

이번 결과는 2026-08-28 결과의 “Simple Clock은 유효 AppWidget instance 생성 실패로 판정 제외”를 정정한다. 위젯 선택 화면에서 `draganddrop` 후 설정 화면의 `OK`를 완료하면 SimpleClock의 유효 binding과 `RemoteViews`가 생성되며, 동일 stale-provider 절차에서 Weather와 같은 Launcher NPE가 재현된다.

## 결론

이 문제는 특정 Weather 앱·특정 버전·날씨 위젯 조합에 한정되지 않는다. 비날씨 앱 SimpleClock 2.1.6/code216에서도 `일반모드 위젯 배치 → 간편모드 전환 → 앱 제거·동일 APK 재설치 → 일반모드 복귀` 순서로 AppWidgetService binding만 사라지게 하면 동일한 Launcher line 185→88 NPE가 독립 3회 모두 발생했다.

반대로 개발사가 사용한 `pm clear → force-stop → reboot`는 WeatherWidget4x1의 binding을 제거하지 못했다. 3회 모두 재부팅 전후 `id=27`과 `RemoteViews`가 유지됐고 Launcher crash는 0건이었다. 따라서 이 절차의 미재현은 수정 효과를 보여주는 `runtime PASS`가 아니라 stale-provider 사전조건을 만들지 못한 음성 대조군이다.

## 개발사 절차의 사전조건 결손

Weather 7.7.8/code126의 `WeatherWidget4x1`을 일반모드에 정상 배치했을 때 AppWidgetService에는 `id=27`, provider, `RemoteViews`가 모두 존재했다. 이후 각 cycle에서 아래를 실행했다.

1. `pm clear com.weatherteam.rainy.forecast.radar.widgets`
2. `am force-stop com.weatherteam.rainy.forecast.radar.widgets`
3. 재부팅

`pm clear`와 force-stop 직후 Weather는 `stopped=true`였지만 `id=27` binding은 남았다. 부팅 후에도 binding은 유지됐고 Weather는 AppWidget broadcast로 `stopped=false`가 됐다. crash buffer는 cycle 1~3 모두 Launcher `FATAL EXCEPTION` 0건이었다.

따라서 개발사 검증 절차는 원본 VoC의 핵심 상태인 `Launcher DB stale widget record ↔ AppWidgetService binding 부재`를 만들지 않는다. fixed build 검증에는 아래 정방향 사전조건을 사용해야 한다.

```text
일반모드에서 3rd-party 위젯 정상 배치
→ 간편모드 전환
→ 위젯 앱 제거
→ 동일 APK 재설치
→ AppWidgetService에서 기존 widget id 소실 확인
→ 일반모드 복귀
```

## 원인 범위 해석

직접 재현 앱은 Weather 7.7.8, Weather 7.8.2, AccuWeather 21.1.15-3-rc, SimpleClock 2.1.6까지 확장됐다. 특히 SimpleClock은 날씨앱이 아니므로 Weather SDK·날씨 데이터·특정 버전 조합이 필요조건이라는 가설은 기각된다.

공통 조건은 3rd-party AppWidget의 package lifecycle로 provider instance가 사라졌지만 Launcher DB의 widget record가 남아 `PendingAppWidgetHostView`가 만들어지는 것이다. 현재 Launcher는 `updateAppWidget(null)` 경로에서 null인 content description에 `equals("Google Go")`를 호출한다. 따라서 직접 관찰 범위에서 원인은 Weather가 아니라 generic pending-widget null 처리 누락이다.

다만 진단 상태는 `OBSERVED`로 유지한다. 한 AT-M140에서 정·역 재현과 앱 범위는 충분히 관찰했지만, 개발사가 수정했다고 한 정확한 `AT-M140Z0827U_DAILY_DEV_GMS_849` fixed build가 없어 수정 전후 A/B를 완료하지 못했다.

## 현재 OTA와 fixed build 경계

현재 단말의 incremental은 `RY07260901S`다. 2026-08-28 확인한 Launcher APK는 OTA 전후 byte-identical했고, dexdump에도 line 185의 null guard 없는 `getContentDescription().equals("Google Go")` 경로가 남아 있었다. 이번 SimpleClock 3/3 재현은 이 현재 OTA가 여전히 취약함을 실기로 확인한다.

이 결과를 개발사가 언급한 `AT-M140Z0827U_DAILY_DEV_GMS_849`의 FAIL로 일반화하지 않는다. 해당 exact build를 확보한 뒤 같은 stale state를 데이터 유지 방식으로 적용하여 역방향을 확인해야 한다.

## 다음 확인 항목

1. exact fixed build `AT-M140Z0827U_DAILY_DEV_GMS_849` 확보
