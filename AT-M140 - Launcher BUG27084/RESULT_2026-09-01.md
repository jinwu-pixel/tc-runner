### 보수적 민감도 집계

ordinal 9 첫 시도 `20260901T135852Z`는 당시 분류기가 stale zero-crash를 fixed 판정 gate 부족으로 잘못 `ERROR` 처리했다. 그러나 원시 trigger는 같은 boot에서 30초를 완료했고 General HOME 렌더링, 동일 Launcher PID `31083`, BUG27084 signature 0, exact Launcher APP CRASH exit 0을 모두 남겼다. 사전 원칙상 완결된 trigger 관찰은 코드의 사후 분류 실패와 분리해야 하므로 이를 포함한 보수적 stale 발생률은 **`10/11 = 90.9%`**다. 산출 규칙은 `실제 trigger 실행 + 30초 전후 증거 완결`이며, stale precondition 도달만으로는 분모에 넣지 않고 cell 단위 중복 제거도 사용하지 않는다. 따라서 같은 ordinal 9라도 trigger가 없던 `20260901T140308Z`는 분모 0이다. 선택 bundle의 `10/10`만으로 “항상 발생하는 결정론적 현상”이라고 과대 일반화하지 않는다.

trigger 전에 중단된 campaign 시도 6건(`20260901T115716Z`, `125328Z`, `130054Z`, `131524Z`, `140308Z`, `151403Z`)은 bind/arm/reset gate 실패로 관찰 분모 0이다. 사전 pilot `075514Z`, `075920Z`도 campaign 분모 밖에서 그대로 보존한다.

## 현재 증거의 한계

- 반복 관찰은 provider별·조건별 n=5를 채웠지만, AppWidgetService binding이 매 reset마다 `+1` drift하여 완전 독립 표본은 아니다. 순서를 block 단위로 교대하고 drift를 공개했지만 단일 단말·단일 firmware라는 경계는 남는다.
- 20개 선택 run과 추가 zero-crash trigger 어디에서도 반복 깜빡임 **loop는 재현되지 않았다**. 선택 bundle 기준 `0/20`, 실제 trigger 완결 전체 기준 `0/21`이다. 관찰된 것은 stale 조건의 단일 crash 후 30초 내 회복이다.
- `launcher_stale_record_evidence`는 계속 `INFERRED_ONLY`다. exact old widget ID의 phase-new loader log delta는 선택 bundle `0/20`, 실제 trigger 완결 전체 `0/21`이며 Launcher DB를 직접 읽은 증거가 아니다.
- 따라서 이 문서의 결론은 `OBSERVED`이며 `CONFIRMED`가 아니다. exact fixed build에서 같은 stale-state·표본수·관찰창·drift 계측으로 `0/n`과 safe placeholder/cleanup을 확인해야 수정 효과를 판정할 수 있다.

### 정량 campaign에 적용한 계측

- 관찰 창을 10초에서 **30초**로 늘리고, BUG27084 signature와 로그/exit-info/boot snapshot을 창 종료 후 수집하도록 하네스를 보강했다.
- 결과 원장에 exact launcher package의 신규 `APP CRASH` 수·PID, exact old widget ID loader-log delta 수, loop 여부와 근거를 추가했다.
- loop는 30초 안에 BUG27084 signature가 2건 이상이거나 exact launcher `APP CRASH` exit가 2건 이상일 때만 계수한다. 단일 crash는 loop로 올리지 않는다.
- 이 변경은 host 검증과 20개 선택 bundle 실기를 완료했다. 앞선 4개 10초 A/B bundle은 당시 원문을 그대로 보존하며 새 schema로 소급 재작성하지 않는다.

## 해소책 우선순위

1. **Launcher 펌웨어 수정**: pending widget의 `RemoteViews`/content description이 null인 경우 크래시하지 않고 안전 placeholder로 표시하거나 stale record를 격리·정리한다.
2. **package lifecycle 정합성**: provider uninstall/replace 시 Launcher DB의 위젯 record가 AppWidgetService binding과 함께 정리되는지 보장한다.
3. **운영 예방 우회**: 앱 제거·교체 전 일반 HOME에서 해당 위젯을 먼저 제거하면 stale record가 생성되지 않는지 정·역 검증한다.
4. **응급 복구**: UI가 크래시 루프에 가려진 경우 exact-gated HOME role 복구를 사용한다. 이는 근본 수정이 아니다.
5. **마지막 수단**: Launcher data clear로 stale DB를 초기화할 수 있지만 HOME 배치 손실이 있어 파괴적 복구로 분류한다.
