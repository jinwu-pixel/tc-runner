## 현재 증거의 한계

- formal 2×2의 각 셀은 **n=1**이다. provider별 A 0/1, B 1/1은 정·역 방향을 지지하지만 발생률과 분산을 말할 표본은 아니다.
- 두 B run에서 관찰된 것은 신규 BUG27084 signature 각 **1건**이다. 10초 뒤 HOME 렌더링과 Launcher process가 안정됐으므로, 현장 증상인 반복 깜빡임 **loop를 재현했다고 계수하지 않는다**.
- 두 B run의 `launcher_stale_record_evidence`는 `INFERRED_ONLY`다. exact widget ID의 phase-new `Widget provider not found` 로그나 Launcher DB 직접 증거는 해당 formal run에서 확보되지 않았다.
- 따라서 이 문서의 결론은 `OBSERVED`이며 `CONFIRMED`가 아니다. 다음 비교는 known-bad 독립 fixture 반복으로 기준 발생률을 먼저 확보한 뒤 같은 표본수의 fixed build와 대조해야 한다.

### 다음 cycle부터 적용되는 정량 계측

- 관찰 창을 10초에서 **30초**로 늘리고, BUG27084 signature와 로그/exit-info/boot snapshot을 창 종료 후 수집하도록 하네스를 보강했다.
- 결과 원장에 exact launcher package의 신규 `APP CRASH` 수·PID, exact old widget ID loader-log delta 수, loop 여부와 근거를 추가했다.
- loop는 30초 안에 BUG27084 signature가 2건 이상이거나 exact launcher `APP CRASH` exit가 2건 이상일 때만 계수한다. 단일 crash는 loop로 올리지 않는다.
- 이 변경은 host-only 검증까지 완료됐다. 위 4개 기존 bundle은 당시의 10초 관찰 원문을 그대로 보존하며 새 schema로 소급 재작성하지 않는다.

## 해소책 우선순위

1. **Launcher 펌웨어 수정**: pending widget의 `RemoteViews`/content description이 null인 경우 크래시하지 않고 안전 placeholder로 표시하거나 stale record를 격리·정리한다.
2. **package lifecycle 정합성**: provider uninstall/replace 시 Launcher DB의 위젯 record가 AppWidgetService binding과 함께 정리되는지 보장한다.
3. **운영 예방 우회**: 앱 제거·교체 전 일반 HOME에서 해당 위젯을 먼저 제거하면 stale record가 생성되지 않는지 정·역 검증한다.
4. **응급 복구**: UI가 크래시 루프에 가려진 경우 exact-gated HOME role 복구를 사용한다. 이는 근본 수정이 아니다.
5. **마지막 수단**: Launcher data clear로 stale DB를 초기화할 수 있지만 HOME 배치 손실이 있어 파괴적 복구로 분류한다.

## 남은 검증과 blocker

- exact fixed build `AT-M140Z0827U_DAILY_DEV_GMS_849`는 로컬에 없다.
- 정량 campaign 준비 capture `20260901T075514Z`는 단말이 `mWakefulness=Asleep`인 상태에서 UIAutomator가 `ERROR: null root node returned by UiTestAutomationBridge.`를 반환해 `capture_complete=false`로 fail-closed했다. HOME은 Simple, mutation은 0이며 표본 분모에서 제외한다. 화면을 깨우고 잠금을 해제한 뒤 새 run_id로 재capture한다.
- A/B 독립 fixture용 `reset-fixture` 실기 pilot은 `20260901T075920Z`에서 fail-stop했다. `pm clear com.hnlens.launcher3` 후 Launcher-host binding은 **15개에서 16개로 증가**했고, 기존 ID 15개 중 14개가 남은 채 SearchLite ID `52`, `53`이 새로 생겼다. 15회 poll 동안 동일해 AppWidgetService orphan 정리 조건을 충족하지 못했다. 따라서 이 reset은 독립 fixture가 아니며 정량 표본 분모에서 제외한다.
- reset 실패 직후 자동 cleanup은 단말을 Simple HOME으로 실제 복귀시켰으나 cleanup 판정이 live Simple 상태를 다시 확인하지 않고 direct recovery로 넘어가는 결함을 드러냈다. TDD 보정 후 `restore-0004`가 role holder / resumed activity / UI package 3-way를 재확인해 `fixture_reset_status=FAILED_SAFE`로 정합화했다. 단말 안전 상태는 확보됐고 잔여 원장 debt는 `launcher_data:cleared-uninitialized` 하나다.
- 독립 fixture 조건인 `prior_id_intersection=[]` 및 `after_launcher_host_binding_count=0`이 충족되지 않았으므로 SimpleClock A/B 2-cycle pilot과 나머지 18-cycle campaign은 진행하지 않았다. 기준 완화나 default binding allowlist는 실측 후 별도 설계 판단 대상이며 현재 결과에 소급 적용하지 않는다.
- exact lifecycle 정·역 A/B는 SimpleClock과 AccuWeather 두 provider에서 확보했지만 각 셀 n=1이다. known-bad에서 provider×A/B 각 **독립 fixture n=5**를 우선 수행하고, 발생률이 불안정하거나 경계값이면 n=10으로 확장한다.
- 각 반복은 신규 run_id와 신규 widget ID를 사용하고, 30초 창의 BUG27084 signature 수, exact-package Launcher APP CRASH exit/PID 수, loop 여부, exact old-widget loader-log delta, 복구 결과를 분자/분모로 누적한다.
- fixed build A/B는 known-bad 기준 표본을 확보한 뒤 동일 provider·절차·관찰 창·표본수로 수행한다. known-bad 1/1 대 fixed 0/1만으로 수정 효과를 선언하지 않는다.
- 모든 3rd-party 위젯으로의 일반화에는 provider를 더 늘린 정량 매트릭스가 필요하다.
- fixed-build 판정은 동일 stale-state 동등성을 먼저 증명한 후 HOME 렌더링, Launcher process 안정, line185/88 NPE 0건, placeholder/정리 동작, 정상 위젯 회귀를 함께 확인해야 한다.
