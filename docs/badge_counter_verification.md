# 배지·미확인 카운터 검증 플레이북

> 정립 사례: BUG #26510 부재중 배지 카운트 불일치 (THOR2_J, 2026-07-13 ~ 07-22) + 연관 이슈 #24947 / #26174.
> 적용 범위: **같은 상태를 여러 컴포넌트가 각자 세거나 표시하는 기능** 전반 — 부재중 배지, 미읽음 메시지,
> 알림 카운트, 앱 아이콘 배지 등. 앱 특이 내용은 최소화하고 방법론만 담는다.
> 관련: `docs/device_measurement_pitfalls.md`(측정 함정) · CLAUDE.md §4(진단·재현)

## 1. 개념 모델 — 판정의 전제

### 1.1 "미확인"은 단일 정의가 아니다

플랫폼이 단일 정의를 강제하지 않으면 **컴포넌트마다 자기 해석으로 쿼리를 짠다.** 실제로 AOSP 콜로그는
미확인 상태를 나타내는 컬럼이 **두 개**다.

| 컬럼 | 문서상 의미 |
|---|---|
| `NEW` (API 1) | 항목의 **존재를 사용자가 acknowledge** 했는가 |
| `IS_READ` (API 14) | 사용자가 그 항목과 **실제로 상호작용**했는가 |

→ "미확인 N건"은 구현마다 다른 집합을 가리킬 수 있다. **먼저 어느 컬럼을 키로 쓰는지 실측으로 확정**한다.

### 1.2 SQL 3치논리 — 불일치의 단골 원인 ★

| 술어 | NULL 행 |
|---|---|
| `col = 0` | **제외** |
| `col != 1` / `col <> 1` | **제외** |
| `col IS NOT 1` (null-safe) | **포함** |

두 카운터가 각각 `= 0`과 `IS NOT 1`을 쓰면 **NULL 행이 존재할 때만** 값이 갈린다. 정상 데이터에서는
영원히 재현되지 않으므로, NULL 행을 만들 수 있는 경로를 찾는 것이 재현의 핵심이 된다.

### 1.3 결함 계열 3분류 — 초반 분류용 렌즈

| 계열 | 정의 | 사례 |
|---|---|---|
| **술어 불일치** | 두 **읽기** 경로의 WHERE가 다름 | #26510 (런처 `= 0` vs 미러 `IS NOT 1`) |
| **집계 단위 불일치** | **카운트는 행 단위**, **표시는 그룹 단위** | #24947 (그룹 대표가 최신 통화라 부재중이 안 보임) |
| **트리거 정의 불일치** | 무엇을 '확인'으로 볼 것인가가 경로마다 다름 | #26174 (탭 이탈만으로 읽음 처리) |

셋 다 뿌리는 같다 — **같은 상태를 여러 컴포넌트가 각자 해석**한다. 새 이슈를 만나면 먼저 이 셋 중
어디인지 분류하면 조사 범위가 절반으로 줄어든다.

### 1.4 읽기와 쓰기는 별개 계층이다 ★

카운트 쿼리(읽기)를 고쳐도 **읽음 처리(쓰기)의 대상 조건은 그대로**일 수 있다.

- 읽기가 넓어지고(`IS NOT 1`) 쓰기가 좁으면(`= 0` 대상) → **세지만 지울 수 없는 행**이 생긴다
- 사용자 체감: "배지가 사라지지 않는다" — 원 증상보다 나쁜 회귀
- **일괄 처리 기능을 새로 추가할 때 특히 위험**하다. 새 기능이 곧 bulk 쓰기이기 때문

## 2. 표준 검증 프로토콜

### 2.0 경로 전수 열거 (가장 먼저)

기능이 아니라 **경로**를 센다. 최소 다음을 열거하고 각각의 조건을 확보한다.

```
읽기: 홈 배지 / 모드별 미러 / 부팅 시 초기 로드 / 외부 화면 / 잠금화면 / 위젯
쓰기: 개별 확인 / 목록 조회·이탈 / 알림 정리 / 항목 삭제 / 전체 삭제 / 부팅 시 정리
```

- 로그에 SQL 원문을 찍는 구현이면 그것이 가장 강한 근거다. 안 찍으면 **행동 매트릭스(§2.2)로 역추정**
- 개발자 진술은 **우리 측정과 대조**한다 — 진술과 실제 구현이 다른 사례가 실재한다

### 2.1 통제 코호트 구성

상태 컬럼만 다르고 나머지가 동일한 행을 **한 화면에 연속 배치**한다.

```bash
S=<serial>
NOW=$(adb -s $S shell 'date +%s' | tr -d '\r'); BASE="${NOW}000"
# is_read 미바인드 → NULL
adb -s $S shell "content insert --uri content://call_log/calls --bind number:s:990401 \
  --bind type:i:3 --bind duration:i:0 --bind new:i:0 --bind date:l:$((BASE-10000))"
# is_read=0
adb -s $S shell "content insert ... --bind is_read:i:0 --bind date:l:$((BASE-20000))"
# is_read=1
adb -s $S shell "content insert ... --bind is_read:i:1 --bind date:l:$((BASE-30000))"
```

- **개수를 비대칭으로**: 실 착신 N건과 NULL M건을 같은 수로 넣으면 어느 방향으로 정합됐는지 역산 불가.
  3 vs 6이면 수정 후 6/6은 "NULL 포함 방향", 3/3은 "NULL 제외 방향"으로 즉시 구분된다
- **표시 검증은 실 착신으로** — 합성 행은 목록에 렌더링되지 않을 수 있다(pitfalls §2.2)

### 2.2 행동 매트릭스로 술어 역추정

SQL 원문을 얻을 수 없는 컴포넌트는 **NULL / 0 / 1 세 그룹의 반응**으로 조건을 역산한다.

| 관측값 | 추정 술어 |
|---|---|
| NULL 제외, 0 포함 | `= 0` |
| NULL·0 모두 포함 | `IS NOT 1` 또는 `(= 0 OR IS NULL)` |
| 전건 1일 때 0 | 바인드 값이 1 (`IS NOT 1`) |
| 전건 1일 때 N | 바인드 값이 0 (`IS NOT 0`) — 오구현 |

### 2.3 감소 경로 전수 ★

**카운트가 늘어나는 방향의 수정은 리스크가 「안 줄어든다」 하나뿐이다.** 줄어드는 경로를 전부 밟는다.

```
□ 개별 확인(탭)        → NULL 행 포함 처리되는가
□ 개별 삭제            → 읽음 처리 없이 삭제되는가 / 카운트 반영되는가
□ 전체 삭제            → 행 0인데 카운트만 남지 않는가
□ 알림 정리            → 대상 집합이 다른가
□ 그룹 항목            → 그룹 안에 묻힌 미확인이 처리되는가
□ 최종                 → 배지 0 도달까지 실제로 소진되는가
```

각 단계에서 **양쪽(또는 전체) 카운터가 동시에 같은 값으로 움직이는지**를 기록한다.

### 2.4 표면 전수

카운트가 맞아도 **표면 하나가 다른 소스를 쓰면** 사용자에겐 여전히 불일치다.

```
□ 일반 모드 홈 배지     □ 간편/접근성 모드 홈 배지 (신고 표면일 가능성)
□ 앱 내 탭 배지        □ 외부·커버 디스플레이     □ 잠금화면 · 위젯
□ 모드 전환 왕복 후 즉시 반영되는가
```

### 2.5 표시 vs 카운트 (집계 단위 검증)

- 목록이 **그룹핑**을 한다면, 그룹 대표 속성이 최신 항목으로 잡히면서 **미확인이 시각적으로 사라질 수 있다**
- 검증: 미확인 항목 + 같은 키(번호 등)의 최신 항목을 만들어 **한 그룹으로 묶은 뒤**
  ① 배지가 남는가 ② 목록에서 식별 가능한가 ③ 그룹을 조작하면 안쪽이 처리되는가
- ②가 실패하면 **"배지는 있는데 지울 대상을 찾을 수 없는" 상태** = 실사용 경로의 심각 결함

## 3. 빌드 비교 프로토콜 (수정 검증)

### 3.1 단일 변수 확보 — 데이터 보존 업데이트 ★

수정 전 빌드에서 데이터를 구성한 뒤 **데이터 보존 방식으로 업데이트**하면, **완전히 같은 행**에 대해
빌드만 바뀐 대조가 된다. 초기화 플래시면 이 대조력을 잃는다.

- 업데이트 전 확인: 플래시 방식(in-place vs wipe), 롤백 가능 여부
- 업데이트 전 반드시 확보: 전 행 덤프 / 카운터 로그 / 표면 스크린샷 / 빌드 지문

### 3.2 blind window 확보 — 업데이트 직전 오프라인 로깅 ★★

`adb logcat`으로는 **플래시 중과 업데이트 후 첫 부팅**을 잡을 수 없다. 그런데 카운터 초기 로드가
정확히 그 구간에서 일어난다.

- 업데이트 **직전에 단말 오프라인 로깅(AP)을 켠다**
- 첫 부팅 후 로그를 pull → 수정 전/후 부팅 구간의 카운터·SQL 원문을 **한 로그로 대조**
- 로그 세션의 **빌드 귀속을 로그 내부 값으로 확정**한다 (`ro.build.version.incremental`) — 파일 타임스탬프로 추정 금지
- 범위는 AP만. 관측자 효과가 있으므로 성능·타이밍 주장은 이 상태에서 하지 않는다

### 3.3 판정표를 사전 등록

수정 방향이 미상이면 "두 값이 같다"만으로는 **어떤 수정이 들어갔는지, 심지어 수정이 있었는지도** 판별되지 않는다.
관측 벡터로 가설을 역산할 수 있도록 **측정 전에** 표를 만든다.

| 관측 | 해석 |
|---|---|
| A / A | 넓은 쪽으로 정합 (NULL 포함) |
| B / B | 좁은 쪽으로 정합 (NULL 제외) |
| A / B 유지 | 미수정 |
| 행 집합 소실 | 대조 불가 → 재구성 후 재측정 |

## 4. 판정 기준

- **`runtime PASS` 요건**: 카운트 정합 + 감소 경로 전수 + 표면 전수 + 실사용 회귀(정상 경로가 여전히 동작)
- 카운트만 맞은 상태는 `runtime PASS` 아님 — **부분 확인**으로 표기
- 계측이 죽은 채로 나온 "차이 없음"은 근거가 아니다. **같은 빌드·같은 절차로 값이 실제 움직이는 것**을
  보여준 뒤에야 음성 결과를 신뢰한다(positive control)
- 합성 데이터로만 얻은 결론은 **실 경로 1회 확인 전까지 잠정**

## 5. 설계·요청 시 체크포인트

카운터 관련 수정을 요청하거나 신규 기능을 넣을 때 **문장으로 명시**해야 하는 것들.

```
□ 대상 술어 — NULL 행 포함 여부를 명시 (「is_read = 0」로 쓰면 재발)
□ 읽기·쓰기 조건 일치 — 같은 헬퍼를 공유하는가
□ 적용 범위 — 모드별·표면별 전부인가
□ 트리거 정의 — 무엇을 '확인'으로 볼 것인가 (진입 / 체류 / 이탈 / 탭 전환)
□ 기존 수정과의 관계 — 되돌리는 것인가, 조건을 얹는 것인가 (되돌림이면 원 티켓 판정 번복임을 명시)
□ 복원 vs 신규 — "이전처럼"이 실제로 이전에 있었는지 실측 확인 후 표현할 것
```

마지막 항목이 특히 중요하다. #26510 후속에서 "이전처럼 되돌려 달라"고 쓰려던 두 항목이,
실측 결과 **이전 빌드에도 없던 동작**이었다. 확인 없이 보냈으면 공수 산정과 일정이 어긋났을 것이다.
