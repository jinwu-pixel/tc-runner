## 0-CORR. 정정 (2026-07-13, 사용자 도메인 확인 반영) — 방향 반전

**아래 §0의 "런처=정답·미러=버그" 결론은 틀렸다. 정정한다.**

- 의도된 스펙(사용자 확정): 배지는 **콜로그에서 사용자가 확인(confirm)하지 않은 부재중**을 보여야 하며, 확인 전까지 **남아야 한다**. 이 "미확인" 카운트를 hnlens 미러(`GlobalDataManage`)가 추적 = **54**. **심플모드(54)·다이얼러 Recent 탭(54)이 정답.**
- **노말 런처 배지(2)가 버그 = 미달 계수(under-count).**
- 오류 근원: 내가 시스템 CallLog `is_read=0`(2)을 "확인" ground truth로 가정. **`is_read`는 확인 신호가 아니다** — 부재중 알림 dismiss/목록 표시/UI 변경 시 1로 클리어되므로 "사용자가 콜로그에서 확인함"과 무관. 그래서 총 부재중 67 중 65가 `is_read=1`이지만 그중 52는 **여전히 미확인**(미러 기준).
- 실기 근거: 노말 콜로그 진입 시 **볼드(미확인) 부재중 그룹이 2개보다 훨씬 많음**(연락처A(13)·070-****-****·080-****-****…, 각 그룹이 개별 통화 다수 묶음). 시스템 `new=1`(7)도 `is_read=0`(2)도 54와 무관 → 54는 미러 자체의 "미확인" 상태.
- **내 가역 실험의 해석 반전**: is_read 토글에 런처가 ±1 추종한 것은 런처가 **잘못된 신호(is_read)를 충실히 따른다**는 뜻. 미러의 +52는 phantom이 아니라 **is_read가 잘못 배제한 실제 미확인 backlog 52건**.
- **수정 방향 정정**: 노말 런처 배지가 심플모드·다이얼러 Recent 탭과 **같은 "미확인" 소스(미러)를 쓰도록** 해야 함. 시스템 `is_read` 쿼리를 버리는 것이 핵심. (또는 is_read를 확인 전 클리어하지 않도록.) "노말만 실패" = 노말만 유일하게 시스템 is_read를 소스로 씀.

**개별 탭 확인 메커니즘 실측 (070 단일통화 탭, 원복 완료)**:
- 확인 로직 = 콜로그에서 미확인은 볼드, **개별 항목 탭 → 읽음 처리** (사용자 확정).
- 070(_id=281) 탭 결과: 시스템 `is_read` **0→1 세팅** + 런처 배지 **2→1** + 미러 **54→53** — **세 소스 전부 −1 동기**. adb로 is_read=0 복원 시 셋 다 복귀(런처 2·미러 54).
- 함의: **개별 탭 확인 경로는 정상 작동**(시스템 is_read도 세팅, 런처·미러 둘 다 추종). 문제의 52-gap = **개별 탭 없이** 시스템 is_read가 1로 클리어된 52건(부재중 알림 dismiss/일괄/부팅 등 non-tap 경로) — 이 52건은 시스템 is_read=1이라 런처가 제외하나, 미러엔 "미확인"으로 남아 정답(54). 즉 **시스템 is_read가 개별 탭 외 경로로도 클리어되는 것이 오염원**이고, 런처가 그 오염된 신호를 소스로 쓰는 것이 노말 버그.
- **결정적 fix 포인트**: 개별 탭은 이미 세 소스 동기하므로, (A) 런처를 미러 소스로 바꾸거나 (B) 시스템 is_read를 개별 탭 외 경로(알림 dismiss 등)에서 클리어하지 않도록 — 둘 중 하나. 26174 fix가 is_read 클리어 시점에 관여했는지 확인이 유력 단서.

| **다이얼러 Recent 탭 배지** | **54** | hnlens 미러 store |

**가역 조작 실험 (미확인 2행 is_read 토글, DB 원복 완료)**:

| 시스템 DB is_read=0 | 런처 | 심플모드 | 오프셋 |

**근본 원인**: 심플모드·다이얼러 Recent 탭이 공유하는 **hnlens 콜-미확인 미러 store(`GlobalDataManage`/`UnReadDataHelper`)가 시스템 CallLog와 별개 DB**다. 두 앱이 같은 SQL(`WHERE type=? AND is_read=?`)을 로그하지만 **런처는 시스템 `content://call_log/calls`를, 심플모드는 자체 미러 테이블을 쿼리** → 같은 쿼리·다른 테이블. 과거 52건 부재중이 **시스템 CallLog에선 is_read=1로 일괄 처리됐으나 미러엔 미동기** → 영구 +52. 미러는 신규 부재중·개별 읽음은 동기(±1)하나 **과거 일괄 read 이벤트를 놓쳐 phantom backlog 고착**.

**노말만 실패·심플 OK인 이유(완결)**: 심플모드는 홈 배지도·콜로그도 **같은 (버그) 미러**에서 옴 → 둘 다 54 → **내부 일관** → 정상으로 보임. 노말모드는 런처 배지가 **시스템 CallLog(2, 정확)**, 콜로그(Recent 탭)는 **미러(54, 버그)** → 2≠54 → 불일치 신고. **즉 틀린 값은 배지(2)가 아니라 콜로그/심플의 54.** 런처가 유일하게 진실을 표시.

**초기 분석 정정**: (a) "런처 stale cache" 기각(프로세스 재시작 생존). (b) "런처가 다른 provider를 읽어 under-count" → 방향 정정: 런처는 시스템 CallLog=정답, **미러가 over-count**. (c) 26510 재현조건 "연락처 삭제"는 실기상 필수·충분 트리거 아님(§4) — phantom은 과거 미동기 일괄 read에서 발생. 26174 fix가 시스템 CallLog is_read를 미러 미관측 경로로 일괄 변경했을 가능성이 유력 연결.

**핸드오프(수정 도메인)**: `com.hnlens` `GlobalDataManage` / `UnReadDataHelper.getUnreadMissedCallCount` — (1) 시스템 CallLog를 직접 쿼리(런처처럼)하도록 바꾸거나, (2) 미러를 bulk is_read 변경·주기 시 **전량 reconcile**. 다이얼러 Recent 탭 배지도 이 미러를 공유하는지(같은 hnlens 서비스) 확인. `updateBadgeCount success:false`(Telecom→런처 push 실패)는 별개 항목이나 미러 교정값 전달 부재에 기여.

증거: `issue_2026-07-13_unit115/`(ISS_A 런처 배지 2·ISS_E 다이얼러 Recent 54·라이브 로그).

## 3. 이슈 단말 divergence의 성질 (워크플로 로그 정밀 대조)

초기 가설(stale cache/타이밍 레이스)은 **기각**. 확정된 사실:

1. **지속적 +52 오프셋**: 캡처 시작 16:10:55에 이미 런처=1, 심플=53. 통화 이전부터 존재하는 baseline 격차.
2. **lockstep 증가**: 신규 부재중 1건에 런처 1→2, 심플 53→54 — 정확히 **+1씩 동시 증가, 오프셋 52 보존**. 신규는 양쪽에 반영, 과거 52행만 갈림.
3. **런처 프로세스 재시작(pid 2297→21611)에도 fresh 쿼리가 여전히 2** — 캐시/메모리 상태 아님. DB가 실제로 런처 쿼리에 **2행을 반환**(`cursor count: 2`).
4. onChange "폭풍"(289건)은 콜백 flood일 뿐 **bulk is_read 리셋 아님**(카운트가 단조 증가, 감소 구간 없음).
5. 통화 세션(16:11:47)은 **INCOMING_MISSED**(미응답) — 26174의 "미확인 부재중 존재 중 통화" 시나리오와 시간 일치하나, 그 통화 자체는 양 카운터 +1만 유발.

→ **런처와 심플이 같은 SQL 문자열(`WHERE type=? AND is_read=?`)을 로그하지만 실제로는 다른 결과집합을 반환**. 동일 DB·동일 쿼리·동일 인자면 `cursor.getCount()`가 같아야 하므로, 이슈 단말에선 (a) 런처가 런타임에 다른 술어/인자를 bind 하거나 (b) 런처가 다른/stale CallLog 스냅샷(provider)을 읽는다.

## 4. 실기 결정적 배제 실험 (건강 단말, 전부 가역·원복 완료)

동일 빌드 실기에서 divergence의 후보 원인을 하나씩 조작·측정:

| 실험 | 조작 | 결과 | 결론 |
|---|---|---|---|
| 베이스라인 | — | 런처=심플=DB unread (6/7/8 삼중 일치) | 정상 상태는 완전 동기 |
| T3 목록 열람 | Recent 탭 열기 | is_read 마킹 안 됨, 카운트 유지 | 열람≠읽음 |
| T3 항목 확장 | 행 액션시트 | 해당 행만 is_read=1, **런처·심플 동시** 하락 | 양앱 같은 이벤트에 같이 반응 |
| T2-1 연락처 삭제 단독 | 삭제 | onChange 0·재쿼리 0·불일치 0 | 삭제만으론 트리거 아님 |
| T2-2 연결된 미확인 부재중 + 삭제 | 저장연락처의 is_read=0 존재 상태서 삭제 | stale cached_name만 잔존, **불일치 0** | 삭제+orphan도 트리거 아님 |
| **서브스크립션 판별** | sub1 행 하나 is_read=0 | 런처 7→8, 심플 7→8 (둘 다 카운트) | **런처 SIM 필터 없음 — 가설 DEAD** |
| **`new` 컬럼 판별** | 미확인 행 하나 new=0 | 런처 8·심플 8 (둘 다 카운트) | **런처 new 필터 없음 — 가설 DEAD** |

→ 서브스크립션·new·캐시·레이스 **전부 배제**. 동일 펌웨어 실기에서 런처와 심플은 `is_read=0`을 **완전히 동일하게** 카운트. 즉 이슈 단말의 2 vs 54는 **DB 내용(any column state)으로 재현 불가** → 남은 가능성은 **런처가 다른 provider/스냅샷을 읽음** 또는 **디컴파일해야 보이는 상태의존 인자**. DB 조작으론 못 건드리는 영역.

**건강 단말이 재현 못 하는 이유**: 미확인 부재중이 소량(5~8건)·전부 최근·backlog 없음. 이슈 단말의 52행 desync 상태를 정상 사용으로 축적한 적이 없음.

## 5. 추가 확정 사실

- **배지 = DB 구동, notification 구동 아님**: 건강 단말에서 dialer `count > 5, clear miss call`로 개별 알림이 정리돼 활성 알림 ≈0인데도 런처 배지=8(DB unread) → 배지는 알림 수가 아닌 CallLog 쿼리에서 옴. (이슈 단말의 런처=2가 활성 알림 2와 우연히 일치했을 뿐 — H-C 기각.)
- **콜로그 열람해도 미확인 미소거**: 목록 열람은 is_read 안 바꿈. 개별 항목 확장만 마킹. → 54가 누적 유지되는 정상 동작(이슈 단말 3일 알림 잔존과 정합).

## 6. BUG #26174 / #26510 관계

- #26174/BTS-24947: dialer `MissedCallNotifier.updateMissedCallNotification`의 "미확인 부재중 존재 중 새 통화 연결→배지는 뜨나 콜로그 항목 미굵음" 수정 (count==0 시 알림 정리 + 탭전환만으론 클리어 금지 + count>5 clear). 양 단말 로그에 이 서브시스템 잔재 확인.
